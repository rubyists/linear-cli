== Goal

Replace the monolithic `LinearCli.CLI.IssueHelpers` and
`LinearCli.CLI.Commands` modules with small, workflow-oriented CLI modules.
Preserve every existing command, output, interactive prompt, error shape, and
return contract while making each issue workflow independently understandable
and testable.

This is a structural refactor. It introduces no user-facing command, no
Linear GraphQL operation, no Ash resource/action/code interface, and no change
to the persisted profile or favorites format.

== Context

`app/lib/linear_cli/cli/issue_helpers.ex` is 618 lines and exposes fourteen
public operations. Its 916-line test file covers comment, close/cancel,
workflow-state selection, pull requests, project attachment, update dispatch,
creation, bare-ID expansion, and self-assignment.

`app/lib/linear_cli/cli/commands.ex` is larger still at 1,440 lines. It owns
unrelated top-level commands (whoami/version, team, project, and profile) and
every issue command from list/view through relation management. Its
`issue_commands_test.exs` counterpart is 4,877 lines. Both files have become
the default landing place for unrelated command work simply because their
names are broad.

The module started as a 401-line Phase 6 port of Ruby's single
`CLI::Issue` object. Subsequent phases correctly reused its available entry
points, but added distinct responsibilities:

* Phase 9 added active-profile defaults to issue creation.
* Phase 11 added bare numeric-ID expansion through profiles, favorites, and a
  team prompt.
* Phase 12 added project moves using a pre-resolved project.
* Later issue work added non-interactive creation and status resolution.

The result is not a set of closely related low-level helpers. It is the CLI
orchestration boundary for several independent issue workflows. The generic
`IssueHelpers` name obscures that boundary and makes routine changes touch a
large, highly coupled source and test file.

== Decisions

=== Keep the behavior in the CLI layer

The split remains under `LinearCli.CLI`. These functions resolve interactive
input through `WhatFor`/`Prompt`, print confirmations, and consult `Profiles`
and `Favorites`. Moving them into `LinearCli.Linear` would make the Ash domain
aware of terminal interaction and local CLI defaults, breaking the established
top-to-bottom layering.

The domain continues to own only API-facing actions such as
`Linear.create_issue/4`, `Linear.assign_issue/3`,
`Linear.workflow_states_by_team/1`, and `Linear.attach_issue_to_project/2`.

=== Split by durable user workflow, not one module per function

Create these modules in `app/lib/linear_cli/cli/issue/`:

[cols="1,2,3", options="header"]
|===
| Module
| Public responsibility
| Existing `IssueHelpers` responsibilities moved there

| `LinearCli.CLI.Issue.Identifiers`
| Normalize an issue identifier before lookup.
| `expand_issue_id/1`, including active-profile, favorite-team, and prompt
  fallback.

| `LinearCli.CLI.Issue.WorkflowStates`
| Resolve a completed, cancelled, or explicitly named workflow state for an
  already-loaded issue.
| `cancelled_state_for/2`, `completed_state_for/2`, and the exact/unique-prefix
  matching used by assignment status selection.

| `LinearCli.CLI.Issue.Actions`
| Perform mutations on an already-loaded issue and coordinate `issue update`.
| Comment, close, cancel, description update, project attachment/move, and
  update precedence/normalization.

| `LinearCli.CLI.Issue.Creation`
| Create an issue interactively or under `--yes`.
| `make_da_issue!/1`, required-field validation, strict team resolution, and
  optional-project parameter construction.

| `LinearCli.CLI.Issue.Assignment`
| Look up an issue and assign it to the current user when needed.
| `gimme_da_issue!/2`, viewer resolution, status-ID resolution, and
  already-assigned confirmation.

| `LinearCli.CLI.Issue.PullRequest`
| Gather PR text and invoke `gh pr create`.
| `create_pr!/3` and `issue_pr/2`.
|===

`Actions` deliberately groups mutations on an already-resolved issue rather
than splitting comment, lifecycle, project, and update-dispatch code into
single-function modules. That is the smallest useful boundary: they share
confirmation/error conventions and `update_issue/2`'s documented precedence.

=== Remove the generic facade after one coordinated call-site migration

Do not retain `IssueHelpers` as a permanent delegating compatibility facade.
All production callers are internal to this application, so a facade would
leave the misleading abstraction in place and add one more indirection without
protecting a supported external API.

Migrate `Commands` and the one incidental internal reference directly to the
new modules in the same change, then delete `issue_helpers.ex`. Use local
aliases in `Commands` so command bodies remain readable. The resulting names
retain the established operation names within an explicit workflow namespace:
`Identifiers.expand_issue_id/1`, `Creation.make_da_issue!/1`, and
`Assignment.gimme_da_issue!/2`, for example. Update their specs and docs in
the same change.

The refactor must not leave duplicate implementations or compatibility wrappers
whose sole purpose is forwarding an old helper name.

=== Preserve contracts exactly before improving them separately

This phase preserves current quirks and contracts, including:

* `Actions.update/2` returns `:ok | {:error, reason}`, while the other
  mutation functions retain their existing `{:ok, value} | {:error, reason}`
  shapes.
* Closing/cancelling remains idempotent; the same messages and `:trash`,
  `:reason`, `:status`, and `:cancel` behavior remain intact.
* Workflow states continue to select a sole result directly, prompt among
  several results without an explicit status, and accept case-insensitive
  exact or unique-prefix status names when supplied.
* Bare numeric IDs retain the resolution order: active profile, one/many team
  favorites, then `WhatFor.ask_for_team/0`. Non-numeric IDs still pass through
  unchanged.
* Interactive creation and `--yes` creation keep their present handling of
  labels, project defaults, strict project lookup, and tagged `:smells_bad`
  errors.
* Pull-request invocation keeps its injectable runner and current stdout
  behavior; this refactor must not change shell command arguments.

Potential UX changes such as making unmatched project selection safe, changing
the `smells_bad` vocabulary, or redesigning `issue update` precedence require
their own approved plan and must not be folded into this move-only work.

=== Split commands by CLI command family and remove the forwarding facade

Create these modules in `app/lib/linear_cli/cli/commands/`:

[cols="1,3", options="header"]
|===
| Module
| Commands owned

| `LinearCli.CLI.Commands.System`
| `whoami` and `version`.

| `LinearCli.CLI.Commands.Teams`
| team list, favorite, and unfavorite.

| `LinearCli.CLI.Commands.Projects`
| project list, favorite, unfavorite, and update.

| `LinearCli.CLI.Commands.Profiles`
| profile create, list, use, show, clear, and delete.

| `LinearCli.CLI.Commands.Issues.Read`
| issue list and view.

| `LinearCli.CLI.Commands.Issues.Create`
| issue create.

| `LinearCli.CLI.Commands.Issues.Development`
| issue develop, PR, and take.

| `LinearCli.CLI.Commands.Issues.Mutations`
| issue update, comment, status, and assign.

| `LinearCli.CLI.Commands.Issues.Move`
| issue move, including its one- and bulk-project modes.

| `LinearCli.CLI.Commands.Issues.Relations`
| issue relation list, add, and remove, including their shared result
  rendering and safe multi-target behavior.
|===

The goal is cohesive command-family files, not a file per leaf command.
`Relations` and `Move` are intentionally separate because each has substantial
command-specific resolution/reporting logic. `Mutations` keeps commands that
change an already-resolved issue but do not constitute a larger standalone
workflow. If any resulting module remains difficult to navigate, split it at a
real subcommand boundary in the same namespace rather than restoring a generic
catch-all module.

`LinearCli.CLI` is the sole production dispatcher for the current
`Commands.*` functions. Update it to alias and call the family modules
directly, then delete `commands.ex`; do not retain a permanent
`LinearCli.CLI.Commands` forwarding facade. Update tests to call the owning
module directly. This is internal code, not a supported library API.

== Verified call sites and dependency direction

`LinearCli.CLI.Commands` is the substantive production consumer of
`IssueHelpers`; it expands identifiers for list/update/status-style flows,
creates issues, takes/develops issues through self-assignment, dispatches
updates, and opens pull requests. `LinearCli.CLI` is the sole production
consumer of `Commands`; it dispatches every parsed command through its public
functions. `LinearCli.Profiles` mentions creation only in documentation; it
has no runtime dependency requiring a compatibility facade. The existing test
suite is the other direct consumer and must be split with the code.

The dependency direction after the change is:

----
Commands
  -> CLI.Issue.{Identifiers, Creation, Assignment, Actions, PullRequest}
  -> CLI.Issue.WorkflowStates       (Actions and Assignment only)
  -> CLI.{WhatFor, Projects, Prompt} and {Profiles, Favorites}
  -> Linear                         (domain code interfaces)
----

After the command split, `CLI` replaces the first line with direct calls to
`CLI.Commands.{System, Teams, Projects, Profiles, Issues.*}`. Command-family
modules may depend on the focused `CLI.Issue.*` workflow modules, display and
prompt helpers, and `Linear`; they must not call one another through a deleted
`Commands` facade.

`WorkflowStates` may depend on `Prompt` and `Linear`, but it must not depend
on `Actions` or `Assignment`. `Identifiers` must remain independent of issue
lookup and assignment. This keeps the modules acyclic and prevents a new
catch-all module from re-forming around shared private functions.

== Building blocks

=== 1. Establish the namespace and move pure orchestration boundaries

Add the six modules under `cli/issue/` with focused moduledocs, specs, and only
the aliases each module needs. Move code without semantic edits first. Private
helpers move beside the public workflow that owns them; do not make private
helpers public merely to avoid moving a few lines.

Where both lifecycle and assignment need state-name matching, expose one small,
well-named `WorkflowStates` operation rather than copying its
case-insensitive exact/unique-prefix algorithm. Keep the distinct lifecycle
selection rule (sole state/prompt/no matching state) in that module too, since
it is one workflow-state policy.

=== 2. Migrate CLI command wiring

Replace the `IssueHelpers` alias in `Commands` with aliases for the specific
workflow modules. Update every call site in one coherent change:

* all bare-ID expansion uses `Identifiers`;
* issue create uses `Creation`;
* take/develop/PR preparation uses `Assignment`;
* update/comment/project/lifecycle work uses `Actions`; and
* PR creation uses `PullRequest`.

Use the resulting explicit names in command moduledocs and nearby comments.
Update references in `display.ex`, `profiles.ex`, and any other internal
documentation so no stale `IssueHelpers` module reference remains.

Delete `app/lib/linear_cli/cli/issue_helpers.ex` only after `rg` confirms no
production, test, or documentation reference remains, except the historical
context in this plan and prior plans.

=== 3. Split helper tests by the same boundary

Replace `issue_helpers_test.exs` with focused test modules:

* identifiers and workflow-state resolution;
* actions/update dispatch;
* creation;
* assignment; and
* pull-request behavior.

Extract only genuinely shared test fixtures and request stubbing into a small
test-support module. It may provide constructed issue/team/user records and
the existing operation-name-based GraphQL response stub, but it must not hide
the behavior each test is asserting. Tests keep their current async safety and
must not introduce shared mutable profile/favorites state outside the existing
profile-aware test setup.

Do not duplicate command-level coverage. The refactor must retain the targeted
unit coverage for each workflow and the existing command tests prove that the
renamed wiring still reaches the same authoritative GraphQL boundary.

=== 4. Extract command families and migrate the dispatcher

Move each `Commands` function with its private helpers into the command-family
module that owns its user-facing command. Preserve injectable options used by
tests (`cwd`, `me`, `runner`, and `halt` where applicable), function arities,
and parser-result input shapes. Private helpers stay with their command family;
they do not become broad shared utilities merely to reduce a few lines of
repetition.

Update `CLI`'s dispatch clauses directly to the new modules. Keep parsing,
dispatch selection, `run/3`, and central error handling in `CLI`; this phase
does not move Optimus specifications or alter command dispatch semantics.

Split `issue_commands_test.exs` into focused command-family test modules:
read/create/development, mutations, move, and relations. Extract only shared
fixture and Req-test response helpers needed by more than one module. Also
move the smaller favorites command tests to the owning teams/projects modules
when doing so removes a stale `Commands` reference. Preserve profile-default
coverage in its existing focused test module while updating its aliases.

Delete `app/lib/linear_cli/cli/commands.ex` and its old giant issue-command
test file only after all dispatch, production, test, and documentation
references have moved.

== Tests and verification

Run the app formatter and the focused replacement test modules while moving
each workflow. Before considering the work complete, run the complete app
suite and the repository's normal local gate.

At the behavioral boundary, compare the pre- and post-refactor test coverage
for all of these cases:

* comment success/error; close/cancel success, idempotency, state selection,
  trash option, and error propagation;
* `issue update` comment-first precedence, every recognized action, description
  update, and no-option result;
* interactive and `--yes` issue creation, required fields, profile defaults,
  strict team/project failures, labels, and API errors;
* bare and already-expanded/UUID identifiers, each profile/favorites/prompt
  fallback, self-assignment, explicit status ID, exact status, unique prefix,
  unknown status, and ambiguous status; and
* injectable PR runner, generated title/body selection, and emitted output;
  and
* every top-level/team/project/profile/issue dispatch route, including bulk
  move and multi-target relation reporting, with unchanged human and JSON
  output contracts.

Use `git diff --check` and `rg` for stale `IssueHelpers` references. No live
Linear mutation is needed: the existing Req-test GraphQL stubs are the
authoritative boundary for this move-only refactor.

== Linear issue decomposition

1. *Introduce issue identifiers and workflow-state modules.* Move bare-ID
   expansion and all workflow-state selection/matching code, update direct
   callers, and split their focused tests. This establishes the shared
   dependency used by later work.
2. *Extract issue lifecycle actions.* Move comment, close/cancel, description,
   project move/attachment, and update-dispatch behavior into `Actions`; update
   command wiring and tests. Depends on issue 1 for workflow-state resolution.
3. *Extract issue creation and assignment workflows.* Move both interactive and
   `--yes` creation plus self-assignment/status handling into `Creation` and
   `Assignment`; migrate callers and focused tests. Depends on issue 1;
   otherwise independent of issue 2.
4. *Extract pull-request workflow and remove IssueHelpers.* Move PR behavior,
   complete the coordinated helper call-site/documentation migration, delete
   the old module and test file, and verify no stale helper references. Depends
   on issues 2 and 3.
5. *Extract non-issue command families.* Move system, team, project, and
   profile commands; rewire their `CLI` dispatch clauses and focused tests.
   This is independent of issues 1-4.
6. *Extract ordinary issue command families.* Move read, create, development,
   and mutation commands; rewire dispatch and split their tests. Depends on
   issues 1-4 because the commands use the focused issue workflows.
7. *Extract issue move and relation commands; remove Commands.* Move the move
   and relation families, migrate remaining dispatch/test/documentation
   references, delete `commands.ex` and the giant issue-command test file, run
   complete validation, and confirm no stale `Commands` references remain.
   Depends on issues 5 and 6.

== Acceptance criteria

* `IssueHelpers`, `Commands`, and their monolithic test files are deleted; no
  non-historical source, test, or documentation reference remains.
* Each replacement module has one workflow responsibility and the dependency
  graph remains acyclic.
* Every existing CLI command keeps its command syntax, prompts, output,
  GraphQL calls, return shapes, and error behavior.
* Workflow-state matching exists in exactly one implementation and is reused by
  lifecycle and assignment flows.
* Focused tests retain all current behavior coverage without unnecessary
  duplicated stubbing or command-level tests.
* The complete app suite and normal repository local gate pass, and
  `git diff --check` is clean.
* `AGENTS.md` indexes this plan and describes the replacement CLI modules; no
  Ash-domain document is changed unless the scope legitimately expands through
  a separately approved plan.
